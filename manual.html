youtube-rss-api · Manual rápido

Feeds RSS y API JSON para canales de YouTube, construidos desde la página del canal (sin API key ni navegador headless). Soporta videos, shorts y streams por separado.

Python 3.8+ · stdlib GET · POST · PATCH · DELETE Token compartido RSS 2.0
Arranque Prefijos de URL Tipos de contenido Endpoints Parámetros Ejemplos Respuesta Errores Variables de entorno Notas y límites

1. Arranque rápido

Opción A (recomendada): un archivo .env

# 1) generar feeds + caché (channels.json es la lista de canales)
python3 generate.py

# 2) crear .env una sola vez y poner un token fijo
cp .env.example .env
TOKEN=$(openssl rand -hex 16)
perl -pi -e "s/^YT_API_TOKEN=.*/YT_API_TOKEN=$TOKEN/" .env
# edita .env si hace falta: YT_API_PORT=8000, YT_PUBLIC_READ=1, YT_FEEDS_PUBLIC_BASE=...
chmod 600 .env

# 3) arrancar la API (lee .env solo): JSON en el puerto 8000
python3 api.py

# 4) en otra terminal, servir los XML (los feeds NO los sirve la API)
python3 -m http.server 8001 --directory feeds
Dos puertos: la API responde JSON en 8000; los archivos .xml se sirven aparte (aquí 8001, en producción nginx). YT_FEEDS_PUBLIC_BASE debe apuntar dónde se sirven los feeds (http://localhost:8001 localmente), porque ese prefijo se escribe en los self-links del RSS y en feed_url.
¿Un solo puerto? Usa Docker Compose (sección 11): el contenedor sirve JSON y XML juntos en el puerto 9012.

Los dos scripts (api.py y generate.py) leen .env de la carpeta del proyecto al arrancar. El archivo está en .gitignore, así que no se sube al repositorio. Si una variable ya existe en el entorno, esa tiene prioridad. Para usar otro archivo:

YT_ENV_FILE=/ruta/mi.env python3 api.py

Opción B: variables inline (válidas solo para ese comando)

YT_API_TOKEN="$(openssl rand -hex 16)" \
YT_API_PORT=8000 \
YT_PUBLIC_READ=1 \
YT_FEEDS_PUBLIC_BASE="http://localhost:8000" \
python3 api.py
LíneaQué hace
\ al finalContinúa la orden en la línea siguiente. Las asignaciones se aplican solo al proceso python3 api.py; no quedan en tu shell.
YT_API_TOKEN="$(openssl rand -hex 16)"Genera 32 caracteres hexadecimales con openssl y los usa como secreto compartido. Es obligatorio; sin él la API no arranca.
YT_API_PORT=8000Puerto donde escucha. Por defecto 8099.
YT_PUBLIC_READ=1Abre GET /api/channel/... sin token. El resto de rutas sigue pidiendo token.
YT_FEEDS_PUBLIC_BASE="http://localhost:8000"Prefijo que se escribe en los self-links del RSS y en el campo feed_url de las respuestas JSON.
Ojo con el token: $(openssl rand -hex 16) se ejecuta cada vez que lanzas esa línea. Si reinicias la API con el mismo comando, el token cambia y cualquier cliente que use el anterior empieza a recibir 401. Fíjalo una vez en .env (Opción A) o en el EnvironmentFile de systemd en producción.

Comprobación (cargando .env en la shell para poder usar $YT_API_TOKEN):

set -a; . ./.env; set +a
curl -s "http://localhost:8000/api/health?token=$YT_API_TOKEN"

# o sin exportar nada:
TOKEN=$(grep '^YT_API_TOKEN=' .env | cut -d= -f2-)
curl -s -H "X-API-Token: $TOKEN" "http://localhost:8000/api/health"
Lectura pública: con YT_PUBLIC_READ=1 solo se abre GET /api/channel/.... Todo lo demás (/api/channels, /api/updates, /api/check, escrituras) sigue exigiendo token.
Producción: systemd no usa .env; usa EnvironmentFile=/etc/default/yt-feeds-api (ver deploy/).

2. Prefijos de URL

El mismo router se sirve bajo tres prefijos. Usa el que encaje con tu despliegue:

PrefijoCuándo usarloEjemplo
/api Local o proxy propio. Es el prefijo recomendado para clientes. http://localhost:8000/api/channel/@tvperu/shorts
/yt/api Producción con el nginx de deploy/ (no se tocó). https://feeds.ejemplo.com/yt/api/channels/tvperu/shorts
/channel Alias antiguo, se mantiene por enlaces ya compartidos. No usar en código nuevo. http://localhost:8000/channel/@tvperu/shorts

<key> acepta slug, @handle, id de canal (UC...), URL de YouTube o nombre (exacto o subcadena única). Si el canal no está registrado en channels.json, se resuelve al vuelo contra YouTube y se consulta en vivo, sin escribirlo en la lista.

3. Tipos de contenido

Cada pestaña del canal se pide por separado:

kindQué devuelveLink del item
videos (por defecto)Subidas normalesyoutube.com/watch?v=ID
shortsShorts verticalesyoutube.com/shorts/ID
streamsDirectos y sus repeticionesyoutube.com/watch?v=ID
 
# las tres formas equivalentes de pedir shorts
GET /api/channel/@tvperu/shorts?limit=20
GET /api/channels/tvperu/shorts?limit=20
GET /api/channels/tvperu/videos?kind=shorts&limit=20
Qué tipos descarga el cron: se configura por canal con "kinds": ["videos", "shorts"] en channels.json. Si el canal no lo declara, se usa la variable YT_KINDS (por defecto solo videos). La API puede pedir cualquier tipo en vivo aunque el cron no lo genere.

4. Endpoints

MétodoRutaUso
GET/api/healthEstado y número de canales
GET/api/channelsLista canales; ?videos=1 incluye todos los videos cacheados
GET/api/channels/<key>Un canal con sus videos y conteo por tipo
GET/api/channel/<key>/<kind>Contenido por tipo (videos, shorts, streams)
GET/api/channels/<key>/<kind>Igual que la anterior
GET/api/updatesNovedades; ?since=ISO&channel=slug&kind=shorts&limit=N
GET/api/resolve?q=Buscar canal en YouTube (nombre, handle, id, URL, suscriptores)
POST/api/channelsAlta de uno o varios canales
PATCH/api/channels/<key>Editar name, slug, handle, url, cid
PATCH/api/channelsEdición en lote [{"key": "...", ...}]
DELETE/api/channels/<key>Borrar un canal (feed + caché de todos los tipos)
DELETE/api/channels?keys=a,bBorrado en lote
POST/api/checkRefrescar ahora; {"channels": [...], "kinds": [...]} opcional

6. Ejemplos

Añadir un canal a channels.json

Es una lista JSON; cada canal necesita slug, name, handle y cid, y opcionalmente kinds y lang. Cuidado con las comas entre objetos:

[
  {"slug": "fireship", "name": "Fireship", "handle": "@Fireship", "cid": "UCsBjURrPoezykLs9EqgamOA"},
  {
    "slug": "tvperu",
    "name": "TVPerú",
    "handle": "@tvperu",
    "cid": "UCrAb_x80PtTiN3lCkQOSFPg",
    "kinds": ["videos", "shorts"],
    "lang": "es"
  },
  {
    "slug": "tvperunoticias",
    "name": "TVPerú Noticias",
    "handle": "@tvperunoticias",
    "cid": "UCkZCoc42IipR1ucqJmIehsA",
    "kinds": ["videos", "shorts"],
    "lang": "es"
  }
]
CampoObligatorioSignificado
slugsíIdentificador interno y nombre de archivo (feeds/tvperu.xml). Minúsculas y guiones.
namesíNombre visible en el RSS y en la API.
handlesí@handle (o /channel/UC... si el canal no tiene alias).
cidsíId UC...; es lo que realmente se consulta.
kindsnoPestañas que descarga el cron. Por defecto, YT_KINDS (videos).
langnoIdioma de YouTube (es, en…). Con es los títulos no se traducen al inglés. Por defecto, YT_LANG.

Después de editar el archivo:

python3 generate.py     # crea feeds/tvperu.xml, feeds/tvperu-shorts.xml, etc.

La alternativa por API (escribe el mismo channels.json):

curl -s -X POST -H "X-API-Token: $TOKEN" \
  -d '{"handle":"@tvperu","kinds":["videos","shorts"],"lang":"es"}' \
  "http://localhost:8000/api/channels"

Si no conoces el cid, búscalo con /api/resolve?q= o con:

curl -sL "https://www.youtube.com/@tvperu" | grep -o '"externalId":"UC[^"]*"' | head -1

Últimos 20 shorts de un canal (sin registrarlo antes)

curl -s "http://localhost:8000/api/channel/@tvperu/shorts?limit=20"

Videos normales

curl -s "http://localhost:8000/api/channel/@tvperu/videos?limit=20"

Directos

curl -s "http://localhost:8000/api/channel/@tvperu/streams?limit=10"

Forzar consulta en vivo y limitar a 5

curl -s "http://localhost:8000/api/channel/@tvperu/shorts?live=1&limit=5"

Novedades de las últimas 24 h (solo canales registrados)

curl -s -H "X-API-Token: $TOKEN" \
  "http://localhost:8000/api/updates?since=$(date -u -d '1 day ago' +%Y-%m-%dT%H:%M:%SZ)&kind=shorts"

Registrar un canal para el cron y los feeds

curl -s -X POST -H "X-API-Token: $TOKEN" \
  -d '{"handle":"@tvperu","kinds":["videos","shorts"]}' \
  "http://localhost:8000/api/channels"

Refrescar solo shorts de un canal y ver qué es nuevo

curl -s -X POST -H "X-API-Token: $TOKEN" \
  -d '{"channels":["tvperu"],"kinds":["shorts"]}' \
  "http://localhost:8000/api/check"

Buscar un canal

curl -s -H "X-API-Token: $TOKEN" \
  "http://localhost:8000/api/resolve?q=mckay+wrigley"

7. Forma de la respuesta

Ejemplo real de /api/channel/@tvperu/shorts?limit=20:

{
  "ok": true,
  "channel": "tvperu",
  "handle": "@tvperu",
  "kind": "shorts",
  "tracked": false,
  "live": true,
  "count": 20,
  "returned": 20,
  "feed_url": "http://localhost:8000/tvperu-shorts.xml",
  "videos": [
    {
      "channel": "tvperu",
      "kind": "shorts",
      "id": "EVHLhRnk5zw",
      "title": "Major IRTP deployment for Pope Leo XIV's visit",
      "link": "https://www.youtube.com/shorts/EVHLhRnk5zw",
      "thumbnail": "https://i.ytimg.com/vi/EVHLhRnk5zw/oar2.jpg",
      "first_seen": "2026-11-17T02:21:28+00:00",
      "meta": ["49 views"]
    }
  ]
}
CampoSignificado
channelSlug interno (minúsculas, con guiones).
kindTipo del contenido devuelto.
trackedtrue si está en channels.json; false si se resolvió al vuelo.
livetrue si esta respuesta vino de una consulta a YouTube (no de caché).
count / returnedItems en caché / items incluidos tras aplicar limit.
feed_urlRSS del mismo tipo (requiere token si los feeds están protegidos en nginx).
first_seenPrimera vez que el servidor vio el item. En shorts es la única fecha disponible.
metaEtiquetas de la página (vistas; en videos/streams también la antigüedad, p. ej. "3d ago").

10. Notas y límites

  • Fechas: YouTube no publica la fecha exacta en esas páginas. first_seen es cuando el servidor lo detectó; en videos/streams se siembra con la etiqueta relativa ("3d ago"), pero los shorts no traen antigüedad, así que su fecha es siempre el primer avistamiento.
  • Sin paginación: una carga de la pestaña trae ~48 shorts o ~30 videos. El tope efectivo por defecto es 20 (YT_MAX_ITEMS); pedir más de lo cacheado no devuelve más items.
  • Pestañas separadas: videos no incluye shorts. El feed agregado all.xml suma solo la pestaña de videos.
  • Shorts: miniatura vertical oar2.jpg; los videos usan hqdefault.jpg.
  • Canales no registrados: /api/channel/<key>/<kind> los resuelve en memoria (1 h) y consulta en vivo. No aparecen en /api/channels, /api/updates ni en el cron hasta darlos de alta con POST /api/channels.
  • Lotes: las escrituras devuelven 207 si algún item falla; revisa results[].status (created, exists, updated, deleted, missing, error).
  • nginx: el snippet de deploy/ sigue usando /yt/api/ y sirve los RSS estáticos en /yt/ con token en la query. Este manual no cambia esa configuración.

11. CORS y despliegue

CORS

La API responde con cabeceras CORS tanto en JSON como en XML. Por defecto YT_CORS_ORIGINS=* permite cualquier origen. Para restringirlo:

# .env
YT_CORS_ORIGINS=https://app.example.com,https://admin.example.com
# vacío = sin CORS
#YT_CORS_ORIGINS=

El preflight OPTIONS responde 204 sin token y permite GET, HEAD, POST, PATCH, DELETE, OPTIONS con las cabeceras Content-Type, X-API-Token y Authorization. HEAD funciona en todas las rutas GET. Además, GET /api/health es siempre público (sin token) para los health checks de Docker y Render, y el token de la query se redacta en los logs.

Docker Compose (puerto 9012)

cp .env.example .env       # define YT_API_TOKEN
docker compose up -d --build

curl http://SERVER:9012/api/health
curl "http://SERVER:9012/api/channel/@tvperu/shorts"
curl -o tvperu.xml http://SERVER:9012/feeds/tvperu.xml

Un solo contenedor sirve JSON y XML: escucha en :8000 dentro y se publica en 9012. Los datos viven en el volumen yt-data (/data) y YT_REFRESH_INTERVAL=1800 refresca cada 30 minutos, sin cron. Para que los self-links del RSS y feed_url apunten a tu dominio:

YT_PUBLIC_BASE=https://feeds.example.com docker compose up -d

channels.json se copia a /data en el primer arranque. Los cambios hechos por la API persisten en el volumen: docker compose down lo conserva y docker compose down -v lo borra. Para editarlo a mano:

docker compose exec yt-feeds vi /data/channels.json

Render

render.yaml es un Blueprint: New → Blueprint y elige el repositorio. Usa el mismo Dockerfile, genera YT_API_TOKEN y publica los feeds en https://<servicio>.onrender.com/feeds/<slug>.xml. api.py toma el puerto de PORT y escucha en 0.0.0.0.

Plan gratuito de Render: el disco es efímero, así que los feeds se regeneran en cada deploy. En un plan de pago, descomenta el bloque disk de render.yaml (montado en /data) para conservar channels.json, state.json, cachés y feeds.
Un puerto, dos prefijos: con YT_SERVE_FEEDS=1 los XML se sirven en /feeds/ desde la propia API, así que no hace falta http.server ni nginx para publicarlos. En ese caso los feeds son públicos (los lectores RSS no envían cabeceras); usa un proxy inverso si deben quedar restringidos.
